# Lab-01: Ігровий цикл на requestAnimationFrame (космічний корабель)

Стек: Vite (vanilla JS), Canvas 2D, ESLint + Prettier.

## Запуск

```bash
npm install
npm run dev
```

Відкрити `http://localhost:5173`. Керування: `W`/`↑` — тяга, `A`/`D` або `←`/`→` — поворот,
`Пробіл` — залп зі спарених гармат. Корабель загортається по краях арени (screen wrap, як
в Asteroids), лазери теж загортаються й згасають за ~0.85 с.

## Архітектура

- `src/physics.js` — **чиста** функція `integrate(ship, input, dt)`: жодних звернень до
  `window`/`document`, лише числа на вході й новий об'єкт стану на виході. Це дозволяє
  тестувати фізику окремо від рендеру та колись перевикористати її на сервері для
  мережевої версії.
- `src/input.js` — `createInput()`: замикання, що ховає `keydown`/`keyup`-обробники та
  мутабельний стан клавіш; назовні віддає тільки `getState()` (копія) і `destroy()`.
- `src/loop.js` — `createLoop()`: цикл з **фіксованим кроком симуляції** (accumulator
  pattern). Симуляція виконується рівно `hz` (60) разів на секунду незалежно від частоти
  монітора; рендер викликається раз на кадр rAF з `alpha` для інтерполяції між попереднім
  і поточним станом корабля.
- `src/render.js` — малювання на canvas з урахуванням `devicePixelRatio` (canvas
  масштабується під фізичну щільність пікселів, а малювання ведеться в CSS-пікселях через
  `ctx.setTransform`).
- `src/experiments.js` — три навмисно "зламані" варіанти циклу для експериментів нижче.
- `src/lasers.js` — чисті функції для лазерних пострілів (`spawnTwinLasers`, `updateLasers`),
  той самий стиль без DOM, що й `physics.js`.
- HUD зверху показує `steps/s`, `frames/s` і час останнього кадру в мс.

Перемикання режиму — query-параметр: `?mode=fixed|blocking|interval|variable`.

## Експерименти

Методика для кожного: відкрити `http://localhost:5173/?mode=...`, дати HUD стабілізуватись
~5 секунд, зафіксувати `steps/s` / `frames/s` / `frame time`, а також візуально оцінити рух
корабля. Значення нижче — **шаблон для заповнення реальними цифрами з вашої машини**;
орієнтовний порядок величин вказано, але їх обов'язково треба перезняти самостійно й
вписати сюди перед здачею.

### 1. Блокуючий цикл у кадрі (`?mode=blocking`)

`createBlockingLoop` після кроків симуляції синхронно виконує `busyWait(12ms)` —
зайнятий цикл `while (performance.now() < end) {}` прямо в callback'у rAF.

| Метрика | fixed (норма) | blocking |
|---|---|---|
| frames/s | ~60 | ______ (очікується ~1000/(16.7+12) ≈ 35) |
| steps/s | ~60 | ______ |
| frame time, мс | ~16.7 | ______ (очікується ~28–30) |
| Відчуття керування | плавне | ривками / "залипає" |

**Пояснення через event loop.** JS у браузері однопотоковий: rAF callback виконується в
тому ж потоці, що й обробка вхідних подій (`keydown`/`keyup`) та композитинг/малювання.
Поки `busyWait` крутиться синхронно, потік **нічим іншим зайнятись не може** — браузер не
може ні намалювати вже готовий кадр, ні розпарсити наступну подію клавіатури, вона просто
чекає в черзі подій до звільнення стеку викликів. Результат: кожен кадр коштує
`16.7 мс (природний rAF-тік) + 12 мс (блокування)`, тобто `frames/s` падає приблизно до
`1000 / 28.7 ≈ 35`, а введення відчувається із затримкою, бо обробка клавіш теж чекає в
черзі мікро/макро-задач разом з рендером.

### 2. `setInterval` замість `requestAnimationFrame` (`?mode=interval`)

`createIntervalLoop` викликає `update`+`render` через `setInterval(tick, 16.67ms)` без
акумулятора: один крок симуляції — один виклик таймера.

| Метрика | fixed (норма) | setInterval |
|---|---|---|
| frames/s у активній вкладці | ~60 | ______ (зазвичай трохи нижче/нестабільне, ~55–60) |
| frames/s у фоновій вкладці | ~60 (rAF просто не тікає, CPU не витрачається) | ______ (браузер троттлить `setInterval` до ~1 разу/с) |
| Візуальна плавність | без розривів (v-sync) | іноді мікро-джанк/tearing |

**Пояснення через event loop.** `setInterval` ставить у чергу макрозадачі за годинником
таймера, який **не синхронізований** із циклом композитора/вертикальною розгорткою
монітора — браузер може отримати колбек якраз між двома кадрами компоновки й "втратити"
його до наступного рефрешу, звідси нерівномірний, а не строго 60 Гц, темп кадрів. Головна
різниця виявляється, коли вкладка йде у фон: специфікація HTML і всі сучасні браузери
навмисно **троттлять** таймери у неактивних вкладках (типово до 1 разу/с), тоді як rAF
просто перестає викликатись зовсім, не витрачаючи CPU. Тому при поверненні до вкладки з
`setInterval`-циклом симуляція різко "підстрибує" на купу накопичених кроків, а з
rAF-циклом (`fixed`) — плавно продовжує, бо `maxFrameTime`-обмеження в акумуляторі не дає
"надолужувати" пропущений час.

### 3. Змінний крок замість фіксованого (`?mode=variable`)

`createVariableStepLoop` передає в `update(dt)` "сирий" `dt` поточного кадру rAF напряму,
без акумулятора й без фіксації кроку в 1/60 с.

| Метрика | fixed (норма) | variable step |
|---|---|---|
| Поведінка при короткому лагу (напр. згортання вкладки й повернення) | детермінована, без стрибків (обмежено `maxFrameTime`) | ______ (корабель "телепортується" на великий вектор — тунелює крізь arena wrap) |
| Однакова траєкторія при 60 Гц vs 144 Гц монітор | так (фізика від `hz`, не від дисплея) | ______ (ні — на 144 Гц `dt` менший, drag/thrust інтегруються частіше й траєкторія відрізняється) |
| Відтворюваність (той самий інпут → той самий результат) | так | ні |

**Пояснення через event loop.** rAF викликається браузером один раз перед кожним кадром
компоновки, а от **проміжок часу між викликами не гарантований і не постійний**: він
залежить від частоти оновлення монітора, завантаженості основного потоку іншими
задачами з черги (парсинг, GC, обробка подій) і навіть від того, чи вкладка щойно
повернулась з фону (тоді `dt` може бути кілька сотень мс за один стрибок). Коли цей "сирий"
`dt` іде напряму у фізику без фіксації кроку, симуляція перестає бути детермінованою:
той самий інпут на різних машинах/моніторах дає різну траєкторію, а при одному
аномально великому `dt` (лаг) корабель може за один крок пролетіти відстань, більшу за
розмір арени — це видно як миттєвий "телепорт" замість плавного руху крізь межу
загортання.

## Reflection (для захисту)

- Чому фіксований крок симуляції важливий саме для мультиплеєра/детермінізму, а не лише
  для "плавності"?
- Чому `busyWait` в rAF-колбеку шкідливіший за той самий обсяг роботи, розбитий на кілька
  кадрів (chunked), навіть якщо сумарний час CPU однаковий?
- Чому `maxFrameTime` в акумуляторі — це компроміс, а не "безкоштовний" захист від
  spiral of death? Що ми свідомо жертвуємо, обмежуючи accumulator?
